# Saved by the Thread

Reading the fine print so you don’t have to.

A static shopping-style guide to toys, beds and bedding, ice trays and footwear for babies and toddlers. Each listing shows what its maker says it is made of, what the maker says is absent, and what no page states. Visitors search, filter by product type, brand, materials, standards, age, price and where the shop is, and switch material rules on or off. The site reports what makers and stores say; it does not rate safety or risk.

This repository is the source of truth for the site. Published with GitHub Pages from `main` at https://mchelen.github.io/SaferByTheThread/ (every open pull request gets a preview at `pr/<number>/`).

## Files

- `index.html`, `assets/styles.css`, `assets/app.js`: the site. Plain HTML, CSS and JavaScript; no build step. `app.js` renders every page from the data below and uses clean URLs (`/shop`, `/a/<aisle>`, `/c/<product type>`, `/b/<brand>`, `/p/<product>`, `/search?q=`, `/brands`, `/glossary/<term>`, `/about`, `/saved`, `/compare`). Filters and sort live in the query string (`cat`, `brand`, `price`, `mat`, `std`, `age`, `ship`, `sort`, `all`; `m` and `strict` only when the material filters differ from the defaults). Old `#/…` links still land on the right page, and so do old department and type links (`/d/toys` → `/a/play`, `/c/pads` → `/c/protectors`) through the `was` lists below.
- `404.html`: GitHub Pages serves it for any path with no file; it sends the browser to `index.html` with the requested path in `?p=`, and `app.js` restores it. This is how the clean URLs work on a static host (a deep link does answer with a 404 status before the hand-off).
- `assets/catalog.js`: turns `data.json` into the catalog the shop filters on (price parsing, materials and age facets, the material-rule evaluation, glossary term linking). Shared by the browser and `tools/check.js`.
- `data.json`: every listing (schema 3), the filter criteria and the "questions makers can answer" list.
- `glossary.json` / `glossary.md`: the materials glossary, generated by `glossary_build.py`.
- `img/`: the saved store photos, `img/<key>.jpg` (640 px JPEG). The site keeps its own copy of every photo a store shows for a product (`photos` in each listing); `node tools/photos.js --write [--only <id>]` fetches them for listings that have none yet (`--refresh` to fetch again).
- `tools/check.js`: validates the data (run in CI). `tools/ratings.js`: reads star ratings from store pages for the price check. `tools/serve.js`: a local server that behaves like GitHub Pages (used by the browser tests). `tools/bundle.js`: writes a single-file copy of the site for hosts that serve one HTML file. `tools/prices.js`: checks store pages for current prices (see "Price check").
- `tests/unit/`: `node --test` tests for `catalog.js`, the data and the price parser in `prices.js`. `tests/e2e/`: Playwright smoke tests of the site in Chromium. `tests/visual/`: screenshot comparisons of the key pages (see its README).
- `research/photo-urls.tsv`: photo source URLs from the original toy research.

## Run it locally

```sh
npm run serve                  # node tools/serve.js; then open http://localhost:8000/
```

The server hands paths without a file to `404.html`, as GitHub Pages does, so the clean URLs work. Any other static server works for the home page, but a deep link such as `/c/balls` needs that hand-off (or the server must answer it with `index.html`). Opening `index.html` straight from disk won't load the data (browsers block `fetch` on `file://`); use the server or `node tools/bundle.js` and open `dist/index.html`.

## Check, test and publish

```sh
npm run check                  # validates data.json and glossary.json
npm test                       # unit tests for the catalog rules
npm ci && npx playwright install chromium
npm run test:e2e               # browser smoke tests
npm run test:visual            # visual regression (Docker), see tests/visual/README.md
node tools/bundle.js dist      # optional single-file build
```

CI (`.github/workflows/ci.yml`) runs the check and both test suites on every pull request. `.github/workflows/pages.yml` deploys to GitHub Pages: `main` at the site root, and every open pull request at `pr/<number>/`, with the preview link posted as a comment on the PR. Pages has to be set to deploy from GitHub Actions once (repository Settings → Pages → Source: GitHub Actions). See CONTRIBUTING.md for the PR conventions.

## Price check

`.github/workflows/price-check.yml` runs `tools/prices.js` every Monday at 09:00 UTC (and on demand from the Actions tab, where an optional `limit` input checks only the first N products). The tool fetches every product URL in `data.json` with a browser-like User-Agent and a 20 s timeout, pausing between requests to the same store, and reads the price from JSON-LD `Product`/`offers`, then `product:price:amount` / `og:price:amount` meta tags, then `itemprop="price"`, and for Shopify URLs (`/products/<handle>`) from `<origin>/products/<handle>.js` or `.json`, which names every variant. When a page sells several sizes or options at different prices, the tool picks the one the listing means: a `?variant=<id>` in the product URL, then the product's `variant` hint, then the variant whose title shares the most words with the product name ("Crib", "Soft Sole", "16 x 32"), then the variant priced as recorded; a rule only decides when every variant it picks has the same price. When nothing decides, the product is reported under "Needs a look" with every price on the page and nothing is rewritten. The page's own words about shipping ("Free shipping on orders $99+", "$8.95 flat rate shipping", "Shipping calculated at checkout", or JSON-LD `shippingDetails` for the US) are read into the product's `shipping` field, which the product page shows next to the store. A change counts when the page's USD price differs from the recorded one by more than 2% and more than $1; prices in other currencies are listed without judgement. The same run reads the page's star rating and review count into the product's `rating` (`tools/ratings.js`): JSON-LD `AggregateRating`, the Judge.me review widget, Shopify's reviews metafield, Okendo product data or the Loox badge in the page, and, when only a review app that loads in the browser is there, Yotpo's or Junip's public widget endpoint with the store's public key from the page; schema.org microdata last. A rating with no reviews is none; a page that was read and no longer shows a rating loses it, while a page that could not be read keeps the last one. Pages that block the request (Etsy and Amazon return 403) or carry no structured price are reported, never fatal; the exit code is always 0.

```sh
node tools/prices.js --limit 8 --report /tmp/price-report.md   # try a few, print a Markdown report
node tools/prices.js --write --report price-report.md          # the job's command
node --test "tests/unit/*.test.js"                                  # parser tests, no network
```

Flags: `--limit N` (first N products), `--only id,id` (only these listings), `--concurrency N` (default 4), `--report FILE` (Markdown: summary line, table of changes with the variant each price came from, products that need a look, pages not found or errored), `--write` (update `data.json`). With `--write`, the dollar amount inside a recorded `price` text is replaced only when that text holds exactly one dollar amount and the page's price is in USD (so "$39.50, free US shipping" becomes "$42, free US shipping", while "$24 to $27.50" or "£30" are left for a person to update), every product whose price was found gets `price_checked: "YYYY-MM-DD"`, and `updated` moves to today when a price text changed. The file is written with the same formatting, so the diff is small.

When `data.json` changed, the workflow pushes the branch `prices/auto-update` and opens a pull request into `main` titled "Price check: <date>" with the report as its body; if that pull request already exists it force-pushes the branch and edits the body. For `gh pr create` to work with the workflow's `GITHUB_TOKEN`, enable "Allow GitHub Actions to create and approve pull requests" under repository Settings → Actions → General → Workflow permissions. The report is also kept as a workflow artifact; `price-report.md` is not committed.

## Data

`data.json` top level: `schema: 4`, `updated`, `ask`, `criteria_groups`, `criteria`, `standards`, `aisles`, `types`, `entries`.

Product type is the main axis. Every listing names one `type`; `types` lists them, and `aisles` are only the menu: each aisle lists the types it shows, and a type can sit in more than one aisle (the first aisle that lists it is its home in breadcrumbs). Adding a product type is one entry in `types` plus its id in one or more aisles.

- `types`: `{id, title, short?, intro?, outro?, ages: {min_months, max_months}, room?, contact?, was?}`. `ages` is the usual age range for the type; the Age range filter uses it for listings without a maker's age rating. `room` (nursery, kitchen, bath, outdoors) and `contact` (mouth, food, skin, sleep, hands) describe the type for later facets. `was` lists old type ids that should redirect here.
- `aisles`: `{id, title, blurb, source?, types: [type ids], was?}`, in menu order. `was` lists old department ids (`/d/<id>` redirects to the aisle).
- `criteria_groups`: `{id, title}`, the named sets the material filters are shown in.

`criteria` are the material filters, each `{id, short, label, help, kind, default, term, group}`:

- `kind: "avoid"`: when on, a listing misses if its fact is `"no"`. `"unknown"` only counts when the visitor turns on "Every detail above is stated".
- `kind: "require"`: when on, a listing misses unless its fact is `"yes"` (silicone testing, organic, tanning).
- `kind: "contains"`: when on, listings whose `contains` lists that id miss (latex, leather; both off by default).

Every filter works one way: on = hide items that don't meet it. Labels name what gets hidden. A criterion only judges listings that carry a fact for it, so a new criterion (such as `flame`, added flame retardant chemicals) starts with facts where the checklist already records them and fills in as listings are re-read.

`standards` lists the certifications and test schemes the Standards facet offers: `{id, label, term}`.

`entries` are the listings, in any order (the site orders them by aisle and type). A listing is one product, or several products from the same brand that share the same materials.

Listing fields:

- `id` (unique slug), `type` (a `types` id), `brand`, `line`
- the checklist, as short noun phrases: `uses` (materials named), `free` (stated absent), `unconfirmed` (no page says), `outside` (flagged parts: plastic lid, synthetic foam, unnamed paint, treated wool)
- `facts`: `{criterion id: "yes" | "no" | "unknown"}` for every criterion that applies (omit ones that don't)
- `contains`: `["latex"]` for natural rubber or latex foam, `["leather"]` for leather, suede, sheepskin
- `standards`: ids from the top-level `standards` list that the maker or store names
- `age`: `{min_months, max_months?, text}` when a maker or store states an age rating; without one the listing takes its type's `ages`
- `quote` (verbatim store-page text) or `evidence`; optional `note`
- `img` (main photo key), `img_src` (URL the photo came from); `photos`: optional `[{key, src}]`, every store photo in page order, with `img` equal to the first `key`
- `products`: list of `{name, url, store, price, ships_from, note?, variant?, price_checked?}`. `price` is the text from the store page (the site parses the first dollar amount; pounds, euros, NZ and Canadian dollars are converted roughly). `ships_from` is `"US"`, a country name, or `null` when not recorded. `shipping` is what the store page says about shipping, written by the price check ("Free shipping on orders over $99, $8.95 below"). `variant` is an optional hint for the price check: words from the store's option name ("16 x 32", "Hard Sole") when the page sells several prices and the product name doesn't say which. `price_checked` is the date the price check last found a price on the page. `rating` is the star rating the store page shows, written by the price check: `{value, count, via, checked}` (`value` out of 5, `count` reviews, `via` where on the page it was read: `json-ld`, `judge.me`, `shopify`, `okendo`, `loox`, `yotpo`, `junip` or `microdata`, `checked` the date). The product's `url` is the page the reviews are on. The site shows the rating from the store with the most reviews on cards and at the top of the product page, and each store's or option's own rating in the buy box.

The "Made with" facet is derived from `uses` and `outside` by the patterns in `assets/catalog.js` (`MATERIALS`). The Age range facet (birth to 6 months, 6 to 12 months, 12 to 24 months, 2 to 3 years, 3 to 5 years, 5 years and up) matches every band a listing's age range overlaps: from the maker's rating, open-ended up to the type's upper age, or the type's `ages` when no rating is recorded.

## Adding listings

1. Add the entry to `entries` in `data.json` with its `type` and every field above (add the type to `types` and an aisle first if it is new). Record items that miss the default rules too; nothing is left out of the data.
2. Save its photo as `img/<key>.jpg` (640 px max, JPEG) and set `img`.
3. `node tools/check.js`, then open the site locally and look at the listing.
4. Commit and push; Pages redeploys from `main`.

## Glossary

Edit `glossary_build.py`, then run `python3 -I glossary_build.py .` to regenerate `glossary.json` and `glossary.md`. Checklist chips link to terms through the `TERM_KEYS` list in `assets/catalog.js`; when you add chip wording or a new term, add or extend its pattern there.

## Tone

The site takes no position on safety or risk. It helps parents and guardians navigate information and choices. Write facts: what a maker says an item is made of, what it says is absent, what nobody states. No "top pick", "skip", "avoid", "safe".
